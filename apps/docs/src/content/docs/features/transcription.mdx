Imagecaster は文字起こし機能を内蔵していません。外部の文字起こしサービスと連携するためのキューイング仕組みを提供しています。

## 仕組み

```
Worker                      外部文字起こしサービス
   │                                │
   │ アップロード完了後              │
   ├─ transcribeStatus: "pending"   │
   │                                │
   │◄─ GET /api/transcription/queue ┤  （定期ポーリング）
   │                                │
   ├─────────────────────────────► ─┤  音声・話者トラックをダウンロード
   │                                │  Whisper 等で処理
   │                                │  （話者トラックがあれば話者を判定）
   │                                ├─ transcript.raw.json を R2 に PUT
   │                                │
   │◄─ POST /api/episodes/:id/      │
   │       transcription-complete ──┤
   │                                │
   ├─ 生データを検証                 │
   ├─ 整形（統合・誤字修正）        │
   ├─ transcript.json / .vtt を保存  │
   ├─ transcribeStatus: "completed" │
   └─ transcriptUrl を更新          │
```

生データ（`transcript.raw.json`）と公開用（`transcript.json` / `transcript.vtt`）を分けて
保存しています。統合の条件や誤字の辞書を変えたときに、文字起こしをやり直さずに
公開用だけを作り直せるようにするためです。

## 文字起こしキュー API

### GET /api/transcription/queue

文字起こし待ちのエピソードを取得します。このエンドポイントを叩くことで、取得したエピソードにソフトロックが掛かります。

```typescript
interface TranscriptionQueueResponse {
  episodes: TranscriptionQueueItem[];
}

interface TranscriptionQueueItem {
  id: string;
  slug: string;
  title: string;
  audioUrl: string;
  sourceAudioUrl: string | null;
  duration: number;
  lockedAt: string;              // ロック取得時刻（1時間で自動解除）
  // 話者トラックがアップロードされている場合のみ
  tracksZipUrl?: string | null;  // zip のダウンロード URL（Presigned）
  speakerTracks?: Array<{
    track: number;               // zip 内のトラック番号
    label: string | null;        // 話者名。null は BGM 等の非発話トラック
  }>;
  // 同時発話を検出する範囲（冒頭からの秒数）。null なら検出しない
  simultaneousUntilSec?: number | null;
  // エピソードの概要（HTML）。冒頭の要約を Whisper の initial_prompt に足す
  description?: string;
  // 参考リンク（タイトルのあるものだけ）。その回の固有名詞の綴りの根拠として、
  // 文字起こし側が hotwords の抽出元と LLM 校正の語彙に足す
  referenceLinks?: Array<{ url: string; title: string }>;
  // すでに文字起こしがあるか（取り直し）。通知の宛先を絞るのに使う
  isRetranscribe?: boolean;
  // これまでに学習した、行頭の架空の話者ラベル（「深井」「ヤンヤン」）。
  // 文字起こし側が Whisper の出力から剥がす
  hallucinationLabels?: string[];
}
```

### ソフトロック

- キューから取得したエピソードは `transcriptionLockedAt` がセットされる
- 他のサービスインスタンスが同じエピソードを二重処理しないための仕組み
- ロックは **1時間** で自動解除（タイムアウト時に `failed` ではなく `pending` に戻る）

### 完了通知

```
POST /api/episodes/:id/transcription-complete
```

```typescript
{
  transcribeStatus: "completed" | "failed",
  duration?: number,        // 音声の実際の長さ（秒）
  errorMessage?: string     // 失敗時のエラー内容
}
```

完了通知前に、文字起こしサービスは `transcript.json` を R2 の以下のパスに PUT してください:

```
episodes/{storageKey}/transcript.json
```

VTT への変換は Worker 側が行い、`episodes/{storageKey}/transcript.vtt` として保存します。

#### 完了通知のレスポンスと再送

| ステータス | 意味 | 呼び出し側の対応 |
|---------|------|---------------|
| `200` | 完了 | — |
| `400` | JSON が不正（パース失敗・構造不正） | 内容を直して再アップロード |
| `404` | エピソードが存在しない | — |
| `500` | 想定外のエラー | リトライする |
| `503` | `transcript.json` がまだ R2 から見えない | バックオフしてリトライする |

Presigned URL（S3 API）で PUT した直後は、Worker 側の R2 バインディングからそのオブジェクトがまだ見えないことがあります。その場合 `503` を返し、`transcribeStatus` は `transcribing` のまま維持します。

:::caution
完了通知が失敗しても、`transcript.json` のアップロードが済んでいるなら `failed` を送らないでください。サーバ側では処理が完了しているのに応答だけが失われた場合、`failed` を送ると成功済みの結果を上書きしてしまいます。ロックを解放して次のポーリングに任せてください。

なお `failed` を `errorMessage` 無しで送っても、既に記録されているエラーメッセージは上書きされません。
:::

### リトライ

`transcribeStatus: "failed"` のエピソードは、管理画面または API からリトライできます:

```
PUT /api/episodes/:id
{
  "transcribeStatus": "pending"
}
```

## 公開サイトでの見え方

エピソードページでは、文字起こしが 2 か所に出る。

| 場所 | 何が出るか |
|------|-----------|
| プレイヤー直下 | 再生中の字幕。いま喋っているところと、その一つ前の 2 行 |
| 概要の下 | 文字起こしの全文。再生中の行に背景が付き、クリックでその位置から再生 |

字幕は再生を始めるまで出ない。読むだけの人に空の枠を見せないため。

### 字幕の割り方

VTT のキューは字幕 1 枚ではなく「ひと続きの発言」で、実測で最長 30 秒・173 字ある。
再生時間の 6 割はそういう長いキューが占めるので、そのまま出すと字幕が止まって見える。

そこで `apps/web/src/lib/captions.ts` が、キューを 28 字ほどに割り直す。

- 区切りは句読点（`。、？！…」』）`）を優先する
- 句読点が来ないまま上限に達したときは、ひらがなの後ろ（助詞の切れ目）→ 文字種の
  変わり目、の順に探して切る。`Apple Watc / h` のような割れ方を避けるため
- 余りが 8 字未満なら前の字幕にくっつける。上限は 32 字

字幕の開始時刻は、キューの尺をそこまでの文字数で按分して求める。話速は中央値
6 字/秒でほぼ一定なので、按分でもズレは 1〜2 秒に収まる。VTT の終了時刻が
取れないときは、次の発言の頭、それも無ければ 6 字/秒 で見積もる。

字幕の枠は常に 2 行ぶんの高さを取る。入れ替わるたびに下の内容が動かないようにするため、
1 枚の上限は 320px 幅でも 2 行に収まる長さにしてある。

## skipTranscription オプション

エピソード作成時に `skipTranscription: true` を指定すると、文字起こしをスキップできます。

```json
POST /api/episodes
{
  "title": "第1回",
  "skipTranscription": true
}
```

この場合、`transcribeStatus` は `skipped` のままになり、キューには追加されません。

API のデフォルトは `false`（文字起こしを実行）です。管理画面の新規エピソード作成フォームでも、「文字起こしをスキップ」チェックボックスは初期状態でオフになっています。

<Aside type="note">
文字起こしサービスの実装例については `docs/TRANSCRIBER.md` を参照してください。
</Aside>

## 整形のやり直し

Whisper の生出力は `transcript.raw.json` として残るため、文字起こしを実行し直さずに
統合の条件や誤字の辞書だけを適用し直せます。

### POST /api/episodes/:id/transcript/reprocess

1 エピソードの公開用ファイル（`transcript.json` / `transcript.vtt`）を作り直します。

```typescript
{
  success: boolean;
  segments: number;   // 整形後のセグメント数
  applied: Array<{    // 効いた置き換えルールと件数
    from: string;
    to: string;
    count: number;
  }>;
}
```

話者分離の導入前に作られたエピソードには生データがありません。その場合は
整形前のデータが入っている `transcript.json` を一度だけ生データとして複製し、
以後の入力にします。複製しないと、整形済みのファイルを入力にしてしまい
統合や置き換えが二重にかかります。

### POST /api/episodes/:id/transcript/corrections

校正で見つかった修正を登録します。文字起こしを回すマシンが、ローカルの `claude` に
校正させた結果を送ってきます。

```typescript
{
  corrections: Array<{
    from: string;     // 置換前
    to: string;       // 置換後
    note?: string;    // なぜ誤認識と判断したか
    general?: boolean; // 番組全体の辞書への提案にも載せるか
    // 出どころ。通読の名指しで確定したものを、あとの見直しで触らせないために持つ
    source?: "glossary" | "review" | "readback" | "suspicion" | "human";
    // 当てる行の時刻（秒）。省くと、いまの本文で当たる全箇所
    at?: { start: number; end: number };
  }>;
  // 行頭に繰り返し付いていた架空の話者ラベル（「深井」）。審査なしで番組の設定
  // hallucination.leadingLabels に足し、次の回からキューの hallucinationLabels で返す。
  // 空白を含むもの・8 文字を超えるものは捨てる
  leadingLabels?: string[];
}
```

`general: true` のものは番組全体の辞書への**提案**として溜まります（人が管理画面で
承認するまで辞書には入りません）。`general` に関わらず、その回では効かせます。

#### この回かぎりの修正は、場所を決めて保存する

修正は「ある時点の本文の、ある箇所についての判断」です。届いた修正は、登録の時点で
**いまの本文のどこに当たるか**を決め、行の時刻と `from` の前後 8 文字を添えて保存します
（`EpisodeMeta.transcriptCorrections[].anchor`）。

| 届き方 | 保存のされ方 |
|---|---|
| `at` あり | その時刻にいちばん長く重なる 1 行の中で見つかった箇所だけ（**行の中に複数あれば全部**）。隣の行には当たらない |
| `at` なし | いまの本文で当たる全箇所に展開（1 箇所につき 1 件） |
| 本文に `from` が無い | 保存しない（`unmatched` に数える） |

整形のときは、保存した順に、それぞれ決まった 1 箇所だけに当てます。前後の文字まで
一致しない修正は当てません。その判断の対象だった本文がもう無いということなので。

- 校正は公開中の本文（既にある修正まで当たったもの）を読んで直しを挙げてくるので、
  `from` はその本文から探します。前の修正が作った本文をさらに直す連鎖
  （鉱山 → 高山 → 高地）は、順に当たるのでそのまま動きます
- 同じ本文に校正をもう一度回して同じ直しが届いても、その `from` はもう本文に無いので
  二重にはなりません
- **取り直し**（`transcription-complete` で新しい生データが届いたとき）には、新しい本文に
  合わない修正を失効させて消します。合うものは残ります

以前は回全体の文字列置換として持っていました。取り直しをまたいで規則が積み上がり、
正しい本文を壊しました。#281 では `悲劇 → 喜劇` と `喜劇 → 悲劇` が別々の取り直しで
入り、最初から正しかった「喜劇か悲劇か」が「悲劇か悲劇か」になって公開されました。
`不安 → ぶあー`（「不安って開発する」用）は「不安障害」まで書き換えました。625 件の
規則のうち、実際に本文を変えていたのは 88 箇所でした。

古い形の規則（`anchor` なし）は、次に整形したときに「そのとき実際に変えている箇所」への
修正に書き直されます。**本文は 1 文字も変わりません**（壊れている箇所も含めてそのまま
写します）。ただし古い形のまま取り直しが来ると、新しい本文のどこに当たるべきかが
分からないので捨てます。

**`at` を付けても、その行の中に `from` が複数あれば全部に当たります。** 「悲劇か悲劇か」の
1 つ目だけを直したいときに `悲劇 → 喜劇` を送ると「喜劇か喜劇か」になります（#281 で
実際に起きました）。1 箇所に絞るには、`で悲劇 → で喜劇` のように、行の中で 1 回しか
現れない形になるまで前後の文字を含めます。文字起こし側の見直し（suspicion）はそうして
送ってきます。

**行まるごとの `from` は避けてください。** Worker の整形が変わって行の区切りが動くと、
どの行にも一致しなくなります。#283 と #285 では、校正が行まるごとで登録していた修正
（尺 → 癪、建て替え → 立て替え など 6 件）が、整形のやり直しで効かなくなりました。

**手で送るときは `at` を付けてください。** `at` の無い修正は、校正が見ていない箇所も
含めて、いまの本文で当たる全箇所に展開されます。文字起こし側は「指摘されていない箇所にも
当たる規則」を行ごとの置換に落としてから送ってきますが、API に直接送るとその検査を
通りません。実際に `加速度 → 経験則` を送って、本文の正しい「加速度センサー」まで
「経験則センサー」になりました。間違えて入れたものは DELETE で、`at` を付けて
その 1 箇所だけ外せます。

「この回全体に効き続ける規則」はありません。展開は登録のときの 1 回きりで、取り直しで
新しく出てきた同じ誤りには当たりません（取り直しのあとは校正がもう一度走ります）。
どの回でも効かせたいものは番組の辞書に入れます。

登録後、そのエピソードの整形が自動でやり直されます（`corrections` が空で
`leadingLabels` だけのときはやり直しません。文字起こし側が既に剥がしているためです）。
文字起こしがまだ無い回に修正を送ると 400 を返します。

```typescript
{
  success: boolean;
  proposed: number;           // 辞書への提案として溜めた件数（既にあるものは数えない）
  episodeRules: number;       // この回かぎりの修正の件数（1 箇所につき 1 件）
  anchored: number;           // 今回届いたうち、場所が決まって保存した件数
  unmatched: number;          // 今回届いたうち、本文に当たる場所が無く捨てた件数
  leadingLabelsAdded: number; // 新しく学習した行頭のラベルの件数
  segments: number;
  changed: number | null;     // 前の本文と違う行の数
}
```

`transcript.json` の `appliedRules.episode` は実際に当たった件数、`episodeUnmatched` は
本文が合わず当たらなかった件数です。統合の条件を変えて行の形が変わると増えます。

### DELETE /api/episodes/:id/transcript/corrections

この回の修正を外します。

```typescript
{ from: string; to?: string; at?: number }
```

`to` を省くと、その `from` の修正をすべて外します。修正は 1 箇所につき 1 件なので、
同じ `from` / `to` が複数箇所にあればすべて外れます。`at`（秒）を付けると、その時刻の
行に当たるものだけを外します。#281 の `不安 → ぶあー` は「不安って開発する」では正しく、
「不安障害」では誤りでした。外したあとは整形をやり直します。

### PUT /api/episodes/:id/glossary

校正の前に文字起こしを通して読んで集めた、その回の用語集を登録します。
`episodes/{storageKey}/glossary.json` に保存します。

```typescript
{
  terms: Array<{
    term: string;        // 正しいと確かめた綴り
    kind?: string;       // サービス名 / 人名 / 専門用語 / 造語 / 店名
    note?: string;       // 何のことか。本文のどこに出てくるかも書かれている
    asWritten?: string;  // 本文での書かれ方（正しい綴りと違うことがある）
    notable?: boolean;   // 参考リンクに載せる価値があるか
    url?: string;        // 参考リンクの URL（Web で確かめたものだけ）
    evidence?: string;   // 綴りを確かめた根拠
    suspects?: Array<{ index: number; text: string; guess?: string }>;
  }>;
}
```

`url` は `http` で始まるものだけを受け取ります。綴りが確かめられなかった語は
文字起こし側で落としているので、ここに届くのは裏の取れたものだけです。

**本文には触らないので、置換規則のような承認は挟みません。** 番組の用語辞典の
材料として残すもので、読み物として出すときに人が選びます。

### GET /api/episodes/:id/glossary

その回の用語集を返します。集めていない回は `{ terms: [], collectedAt: null }` です。

### POST /api/transcription/reprocess-all

公開済みエピソード（`index.json` に載っているもの）をまとめて再処理待ちに積みます。

```typescript
{ success: boolean; queued: number }
```

全件を 1 リクエストで処理すると Worker のリソース制限に達するため、対象を
`index.json` の `transcriptReprocessIds` に積み、Cron が 1 回あたり 10 件ずつ
消化します。すべて終わると公開サイトのビルドが走ります。
