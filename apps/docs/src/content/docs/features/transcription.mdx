Imagecaster は文字起こし機能を内蔵していません。外部の文字起こしサービスと連携するためのキューイング仕組みを提供しています。

## 仕組み

```
Worker                      外部文字起こしサービス
   │                                │
   │ アップロード完了後              │
   ├─ transcribeStatus: "pending"   │
   │                                │
   │◄─ GET /api/transcription/queue ┤  （定期ポーリング）
   │                                │
   ├─────────────────────────────► ─┤  音声・話者トラックをダウンロード
   │                                │  Whisper 等で処理
   │                                │  （話者トラックがあれば話者を判定）
   │                                ├─ transcript.raw.json を R2 に PUT
   │                                │
   │◄─ POST /api/episodes/:id/      │
   │       transcription-complete ──┤
   │                                │
   ├─ 生データを検証                 │
   ├─ 後処理（統合・誤字修正）        │
   ├─ transcript.json / .vtt を保存  │
   ├─ transcribeStatus: "completed" │
   └─ transcriptUrl を更新          │
```

生データ（`transcript.raw.json`）と公開用（`transcript.json` / `transcript.vtt`）を分けて
保存しています。統合の条件や誤字の辞書を変えたときに、文字起こしをやり直さずに
公開用だけを作り直せるようにするためです。

## 文字起こしキュー API

### GET /api/transcription/queue

文字起こし待ちのエピソードを取得します。このエンドポイントを叩くことで、取得したエピソードにソフトロックが掛かります。

```typescript
interface TranscriptionQueueResponse {
  episodes: TranscriptionQueueItem[];
}

interface TranscriptionQueueItem {
  id: string;
  slug: string;
  title: string;
  audioUrl: string;
  sourceAudioUrl: string | null;
  duration: number;
  lockedAt: string;              // ロック取得時刻（1時間で自動解除）
  // 話者トラックがアップロードされている場合のみ
  tracksZipUrl?: string | null;  // zip のダウンロード URL（Presigned）
  speakerTracks?: Array<{
    track: number;               // zip 内のトラック番号
    label: string | null;        // 話者名。null は BGM 等の非発話トラック
  }>;
}
```

### ソフトロック

- キューから取得したエピソードは `transcriptionLockedAt` がセットされる
- 他のサービスインスタンスが同じエピソードを二重処理しないための仕組み
- ロックは **1時間** で自動解除（タイムアウト時に `failed` ではなく `pending` に戻る）

### 完了通知

```
POST /api/episodes/:id/transcription-complete
```

```typescript
{
  transcribeStatus: "completed" | "failed",
  duration?: number,        // 音声の実際の長さ（秒）
  errorMessage?: string     // 失敗時のエラー内容
}
```

完了通知前に、文字起こしサービスは `transcript.json` を R2 の以下のパスに PUT してください:

```
episodes/{storageKey}/transcript.json
```

VTT への変換は Worker 側が行い、`episodes/{storageKey}/transcript.vtt` として保存します。

#### 完了通知のレスポンスと再送

| ステータス | 意味 | 呼び出し側の対応 |
|---------|------|---------------|
| `200` | 完了 | — |
| `400` | JSON が不正（パース失敗・構造不正） | 内容を直して再アップロード |
| `404` | エピソードが存在しない | — |
| `500` | 想定外のエラー | リトライする |
| `503` | `transcript.json` がまだ R2 から見えない | バックオフしてリトライする |

Presigned URL（S3 API）で PUT した直後は、Worker 側の R2 バインディングからそのオブジェクトがまだ見えないことがあります。その場合 `503` を返し、`transcribeStatus` は `transcribing` のまま維持します。

:::caution
完了通知が失敗しても、`transcript.json` のアップロードが済んでいるなら `failed` を送らないでください。サーバ側では処理が完了しているのに応答だけが失われた場合、`failed` を送ると成功済みの結果を上書きしてしまいます。ロックを解放して次のポーリングに任せてください。

なお `failed` を `errorMessage` 無しで送っても、既に記録されているエラーメッセージは上書きされません。
:::

### リトライ

`transcribeStatus: "failed"` のエピソードは、管理画面または API からリトライできます:

```
PUT /api/episodes/:id
{
  "transcribeStatus": "pending"
}
```

## VTT フォーマット

```
WEBVTT

00:00:00.000 --> 00:00:05.000

今回のテーマは...
```

## skipTranscription オプション

エピソード作成時に `skipTranscription: true` を指定すると、文字起こしをスキップできます。

```json
POST /api/episodes
{
  "title": "第1回",
  "skipTranscription": true
}
```

この場合、`transcribeStatus` は `skipped` のままになり、キューには追加されません。

API のデフォルトは `false`（文字起こしを実行）です。管理画面の新規エピソード作成フォームでも、「文字起こしをスキップ」チェックボックスは初期状態でオフになっています。

## hideTranscription オプション

`hideTranscription: true` を設定すると、文字起こしが完了していても公開サイトに表示されません。

```
PUT /api/episodes/:id
{
  "hideTranscription": true
}
```

## 後処理のやり直し

Whisper の生出力は `transcript.raw.json` として残るため、文字起こしを実行し直さずに
統合の条件や誤字の辞書だけを適用し直せます。

### POST /api/episodes/:id/transcript/reprocess

1 エピソードの公開用ファイル（`transcript.json` / `transcript.vtt`）を作り直します。

```typescript
{
  success: boolean;
  segments: number;   // 後処理後のセグメント数
  applied: Array<{    // 効いた置き換えルールと件数
    from: string;
    to: string;
    count: number;
  }>;
}
```

話者分離の導入前に作られたエピソードには生データがありません。その場合は
後処理前のデータが入っている `transcript.json` を一度だけ生データとして複製し、
以後の入力にします。複製しないと、後処理済みのファイルを入力にしてしまい
統合や置き換えが二重にかかります。

### POST /api/transcription/reprocess-all

公開済みエピソード（`index.json` に載っているもの）をまとめて再処理待ちに積みます。

```typescript
{ success: boolean; queued: number }
```

全件を 1 リクエストで処理すると Worker のリソース制限に達するため、対象を
`index.json` の `transcriptReprocessIds` に積み、Cron が 1 回あたり 10 件ずつ
消化します。すべて終わると公開サイトのビルドが走ります。
